【第二部分】3 条改进建议

## 建议 1
问题：android_vscreen_launch 的「画面变化：是」会把「首帧到达但为纯白」误报成"画面已刷新"，且完全不检测目标 app 是否秒退。实测：launch 返回「画面变化：是（虚拟屏画面已刷新）」，但紧接着的截图是 6367 字节纯白（720x1280 的 PNG 只有 6KB，本身就说明是单色帧）；logcat 显示 net.csdn.csdnplus/.activity.SplashActivity t1942 在 08:54:48.363 就被 removeAppToken / onTaskVanished（state=DESTROYED），displayId=14 上一个 activity 都没留下，dumpsys 里该 display 只剩一个空 Task。也就是说工具告诉我"画面变了"，实际是"白屏闪过然后就没了"。
建议改法：launch 返回值增加 4 个字段：`firstFrame`（blank/content/absent）、`foregroundActivity`、`appExited`、`exitedAfterMs`；「画面变化」从布尔改成三态文案：「无变化」/「仅首帧到达（空白帧）」/「已绘制非空白帧」。判定方式：截帧统计唯一色数，==1 即判空白；launch 后用 2~3s 轮询该 display 的 ResumedActivity 是否仍属于目标包，已退出就回 `appExited=true` 并附最后 Activity 名。文案示例：「首帧已到达但为纯白空白帧；SplashActivity 已于 412ms 后退出，目标 app 未在 displayId=14 呈现界面」。
影响：本任务里为了确认"launch 之后到底渲染没有"，我额外花了 1 次 see + 1 次文件字节比对 + 1 次 dumpsys activity + 1 次 logcat 才看清真相，共 4 次调用；有这 4 个字段可省掉 3 次，并避免把白屏当成"app 已就绪"、随后对死屏做无效交互的误判。

## 建议 2
问题：android_vscreen_tap / android_vscreen_swipe 在事件被 InputDispatcher 丢弃时依然返回「操作成功。」，且不返回 changed/命中窗口。实测两条原文：`Dropping event because there is no touchable window at (360.0, 640.0) on display 14.`（tap）与 `Dropping event because there is no touchable window at (360.0, 1000.0) on display 14.`（swipe）。返回体里没有任何字段能区分"点中了"和"被丢了"，我只能再补一次 vscreen_see + 跑 md5sum/cmp 才发现前后两帧字节完全一致（6367 bytes / 53e4e6f0572b6cadadf2ab1d946446fc）。
建议改法：tap/swipe 返回体增加 `dropped`（bool）、`reason`（no_touchable_window / display_mismatch / outside_bounds）、`hitWindow`（该坐标命中的窗口名）、`beforeFrameHash`/`afterFrameHash`、`changed`（bool）。文案直接写：「事件已注入但被 InputDispatcher 丢弃：display 14 在 (360,640) 无 touchable window，画面未变化」。changed 用注入前后帧哈希比对即可，不必额外截全图。
影响：本任务 2 次交互各多耗 1 次 see + 1 次 shell 哈希比对，共 4 次调用可全省；更关键是避免把"丢弃"读成"点击成功"，从而写出"点击后进入下一页"这种错误结论。

## 建议 3
问题：android_vscreen_key 两次（KEYCODE_BACK 与别名 back）都返回「按键失败：虚拟屏服务超时」，但事件其实已经发出去，并且落到了 displayId=0 的主屏——logcat 原文 `displayId=0, name='d64b60e com.deepseek.harness/com.deepseek.harness.MainActivity' result='OK'`。等于"在虚拟屏按返回键"实际动的是用户主屏，且工具把"已发出"报成"失败"，好坏两头都错。另外同一时刻 android_vscreen_status 只回「虚拟屏运行中，displayId=14；画面：已有首帧」，查不到前台是哪个包、有没有 activity，"已有首帧"极易被读成"app 正常在跑"（实际是空白帧 + 无 activity）。
建议改法：（1）key 注入禁止 fallback 到其它 display：注入前先校验 display 14 存在 focused window，没有就直接返回 `ok:false, injected:false, reason:no_focused_window_on_display`，绝不允许落到 display 0；把 syncMode=WAIT_FOR_FINISHED 的 30s 等待改成短超时（约 1.5s），并把 `injected/ok/dropped` 如实回传，消除「超时=没生效」的模糊态。（2）status 增加 `foregroundPackage`、`resumedActivity`、`activityCount`、`frameBlank` 四个字段。
影响：本任务正是「key 失败 → 查 status → 再 key 别名重试 → 再查 status」白烧了 3 次调用（第 9~11 步）；补上前述字段后 1 次 status 即可判断"屏空着、没前台包"，同时消除虚拟屏按键误伤主屏这一安全层面的误判。
